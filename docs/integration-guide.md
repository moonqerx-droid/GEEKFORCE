# Руководство по интеграции

Роль: Участник 4 (лидер интеграции).

## Порядок интеграции

1. **Контракты.** API-контракты фиксируются первыми. Пока их нет — все работают на моках.
2. **Первый вертикальный срез.** Как можно раньше должен заработать один путь от первого сообщения до закрытия обращения. Пока он не проходит — необязательные функции не начинаются.
3. **Обязательные сценарии.** Шесть сценариев из раздела 11 `PROJECT_PLAN.md`.
4. **Incident Radar.** Три seed-обращения с общей причиной + четвёртое во время демонстрации.
5. **Стабилизация.** Feature freeze за 3–4 часа до защиты.

## Ежедневный ритуал

- Синк два раза в день, максимум 10 минут.
- После синка: обновить issues, собрать `develop`.
- Ветки обновляются из `develop` минимум два раза в день.

## Чек-лист интеграции

- [ ] `develop` создана от `main`
- [ ] Все feature-ветки ответвлены от `develop`
- [ ] API-контракты зафиксированы
- [ ] Первый вертикальный срез проходит целиком
- [ ] Шесть обязательных сценариев воспроизводимы
- [ ] Incident Radar работает в основном продукте
- [ ] `docker compose up --build` работает на macOS и Windows
- [ ] CI зелёный
- [ ] README содержит рабочие URL
- [ ] Резервная локальная демоверсия готова
- [ ] Сценарий защиты отрепетирован минимум трижды

## Правило приоритетов при нехватке времени

1. Полный основной сценарий.
2. Корректная эскалация.
3. Пять обязательных тестовых случаев.
4. Рабочий Incident Radar.
5. Надёжный деплой и fallback.
6. Визуальная полировка.
7. Дополнительные функции.

Срезаем строго снизу.
