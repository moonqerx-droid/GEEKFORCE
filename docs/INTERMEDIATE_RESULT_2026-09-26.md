## 1. Что мы строим

HelpFlow — web-приложение для внутренней технической поддержки. Сотрудник описывает проблему свободным текстом, после чего система:

1. определяет сервис, симптомы и срочность;
2. задаёт только необходимые уточняющие вопросы;
3. выдаёт действия по одному шагу;
4. фиксирует результат каждого действия;
5. отдельно спрашивает, действительно ли проблема решена;
6. закрывает обращение только после явного подтверждения;
7. при необходимости передаёт специалисту полную карточку контекста.

Главная формулировка для защиты:

> Мы автоматизировали не ответ на вопрос, а весь путь обращения: от эмоционального описания до подтверждённого решения или передачи специалисту с полностью подготовленным контекстом.

Формат продукта — responsive web app. Это оптимально для команды с macOS и Windows: всем нужен только браузер и Docker/Node.js, отдельные нативные приложения собирать не требуется.

## 3. Что реализовано в backend

### 3.1. HTTP API

Работают маршруты:

```text
GET  /health
POST /api/conversations
GET  /api/conversations/{id}
POST /api/conversations/{id}/messages
POST /api/conversations/{id}/step-result
POST /api/conversations/{id}/escalate
GET  /api/operator/tickets
```

Также доступны:

```text
GET /docs
GET /openapi.json
GET /debug
GET /debug/operator
```

FastAPI автоматически публикует актуальные схемы запросов и ответов через OpenAPI.

### 3.2. Управляемый диалог

Состояния разговора:

```text
NEW
  → CLARIFYING
  → TROUBLESHOOTING
  → VERIFYING
  → RESOLVED
  ↘ ESCALATED
```

Backend является единственным источником истины по состоянию. Frontend отображает полученный объект и не пытается самостоятельно вычислять следующий переход.

Реализовано:

- создание и восстановление обращения;
- сохранение всей переписки;
- несколько последовательных уточняющих вопросов;
- выбор следующего шага по известным фактам;
- фиксация `helped`, `not_helped`, `cannot_perform`;
- переход к следующему шагу после неудачи;
- отдельная проверка результата после ответа «помогло»;
- защита от ложного закрытия при фразе «не знаю, работает ли»;
- эскалация после исчерпания сценария;
- ручная эскалация;
- запрет сообщений в неподходящем состоянии;
- запрет изменений после `RESOLVED` и `ESCALATED`;
- сохранение исходного обращения и полной истории.

### 3.3. AI и база знаний

В backend интегрирован модуль участника 3 из `feat/ai-triage`.

Он содержит 11 playbook-сценариев:

1. CRM/рабочая система;
2. пароль и вход;
3. VPN;
4. Outlook/почта;
5. Wi-Fi/сеть;
6. видеозвонки;
7. права доступа;
8. недоступность сервиса;
9. массовый сбой;
10. инцидент информационной безопасности;
11. неизвестная проблема.

AI-модуль умеет:

- классифицировать проблему;
- определять сервис и симптомы;
- извлекать факты и текст ошибки;
- оценивать срочность и объяснять причину;
- выбирать следующий вопрос;
- выдавать подходящий шаг;
- не повторять выполненные шаги;
- интерпретировать подтверждение решения;
- готовить структурированную карточку эскалации;
- работать с OpenAI-compatible LLM;
- полностью работать без ключа через детерминированные правила.

По умолчанию используется `AI_PROVIDER=mock`: внешняя сеть и платный API для демонстрации не нужны. При наличии ключа можно задать `AI_PROVIDER=openai`, `AI_API_KEY`, `AI_BASE_URL` и `AI_MODEL`.

### 3.4. Критические сценарии

Информационная безопасность и массовый сбой обрабатываются как критические случаи.

- Фишинг, взлом или вредоносный файл приводят к немедленной эскалации.
- Пользователь получает безопасную инструкцию, например отключиться от сети и не удалять данные.
- Сообщение «у всех коллег тоже» повышает приоритет до `critical`.
- Критическая информация распознаётся не только в первом сообщении, но и во время уточнения или проверки результата.
- Исходное обращение и поздно обнаруженные обстоятельства сохраняются в карточке.

### 3.5. Карточка эскалации

В `escalation_card` сохраняются:

- исходное обращение;
- краткое описание;
- сервис;
- срочность и её причина;
- известные факты;
- заданные вопросы и ответы;
- выполненные шаги и результаты;
- текущий результат;
- причина передачи;
- рекомендуемая команда;
- AI-резюме;
- источник резюме: правила или LLM.

Специалисту не требуется просить пользователя заново пересказать проблему.

### 3.6. Надёжность и конкурентные запросы

Каждый новый диалог имеет поле `revision`.

Frontend отправляет:

```json
{
  "content": "Ошибка 403",
  "expected_revision": 2
}
```

Для результата шага дополнительно отправляется `step_code`.

Это защищает от ситуаций, когда:

- пользователь дважды нажал кнопку;
- браузер повторил запрос после сетевой ошибки;
- две вкладки одновременно изменяют одно обращение;
- старый ответ относится уже не к текущему шагу.

Устаревший запрос получает `409 Conflict`. Debug UI загружает актуальное состояние и сохраняет набранный текст без автоматического повторения mutation.

Проверен реальный конкурентный сценарий с двумя потоками и двумя SQLAlchemy sessions: сохраняется только один ход.

### 3.7. Хранение данных

Используются SQLite и SQLAlchemy 2.

Основные сущности:

- `Conversation`;
- `Message`;
- `TroubleshootingStep`.

Сохраняются:

- состояние обращения;
- сообщения;
- шаги и их результаты;
- AI-факты;
- заданные вопросы;
- активный шаг;
- результат проверки;
- карточка эскалации;
- связь с будущим массовым инцидентом;
- версия для optimistic concurrency.

### 3.8. Миграции Alembic

Есть три миграции:

| Revision | Назначение |
|---|---|
| `20260925_0001` | таблицы разговоров, сообщений и шагов |
| `20260926_0002` | контекст AI и структурированная эскалация |
| `20260926_0003` | `revision` для конкурентных изменений |

Исправлена важная проблема: Docker Alembic использует тот же `DATABASE_URL`, что и приложение, и мигрирует постоянную базу `/data/helpflow.db`.

Миграции:

- создают новую базу;
- обновляют старую demo-базу без потери обращений;
- проверяют совместимость старой схемы;
- поддерживают offline SQL generation;
- не помечают явно несовместимую схему как успешно обновлённую.

### 3.9. CORS

Разрешены локальные frontend-origin:

- `http://localhost:3000`;
- `http://localhost:5173`;
- `http://127.0.0.1:3000`;
- `http://127.0.0.1:5173`.

Список задаётся переменной `CORS_ORIGINS`. Неизвестный origin не получает разрешающий заголовок.

## 7. Проверенные пользовательские сценарии

### Срочная CRM-проблема

1. «Не могу войти в CRM, через 20 минут встреча».
2. Определяется сервис CRM и `high` urgency.
3. Система уточняет ошибку.
4. Выдаёт подходящий шаг.
5. После «помогло» переходит в `VERIFYING`.
6. После явного «да» закрывает обращение как `RESOLVED`.

### Неуспешная диагностика

1. Пользователь сообщает проблему.
2. Несколько шагов получают `not_helped`.
3. Шаги не повторяются.
4. После исчерпания сценария обращение переходит в `ESCALATED`.
5. В операторской панели появляется полная карточка.

### Неоднозначное подтверждение

Фраза «не знаю, работает ли сейчас» оставляет статус `VERIFYING`. Обращение не закрывается по одному положительному слову внутри неопределённой фразы.

### Информационная безопасность

Фраза о фишинговой ссылке приводит к `critical`, безопасной инструкции и немедленной передаче в отдел информационной безопасности.

### Массовый сбой в сообщении

Фраза «CRM не работает у всех коллег» распознаётся как критический массовый сбой и эскалируется.

### Приветствие перед проблемой

Если первое сообщение — «Привет», система начинает с общего уточнения. Когда пользователь затем называет CRM, сценарий переключается с `unknown` на CRM и обновляет сервис и срочность.

### Две вкладки

Если одна вкладка уже изменила обращение, вторая получает `409`, загружает свежую версию и не теряет введённый текст.

| Риск | Текущее решение |

| LLM/API недоступен на защите | детерминированный rules fallback |

| Разные ОС участников | Docker + web app |
| Повторный запрос или двойной клик | `revision`, `step_code`, `409` |
| Потеря состояния после refresh | SQLite + GET разговора; frontend сохранит ID |
| Галлюцинация AI | сценарий и переходы определяет код |
