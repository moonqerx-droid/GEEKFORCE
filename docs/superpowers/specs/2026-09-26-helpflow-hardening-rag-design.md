# HelpFlow: интеграция, надёжный RAG и подготовка демо

**Дата:** 2026-09-26  
**Статус:** согласованное направление, готово к техническому планированию  
**Цель:** собрать ветки команды в устойчивый вертикальный сценарий и превратить локальную Qwen в контролируемого помощника, который отвечает только по утверждённой базе знаний и передаёт обращение оператору при недостатке данных.

## 1. Результат

К ближайшей интеграционной точке пользователь должен пройти один из трёх полностью рабочих путей:

1. получить безопасное решение и подтвердить результат;
2. получить несколько диагностических шагов и затем полную эскалацию;
3. быть немедленно переданным специалисту при опасном, неизвестном или неуверенно распознанном запросе.

Основной критерий качества — повторяемый сквозной сценарий через React-интерфейс, FastAPI, PostgreSQL, базу знаний и локальную `qwen3.5:9b`. Интерфейс, AI и операторская очередь не считаются готовыми по отдельности, пока общий сценарий не проходит на чистом запуске.

## 2. Принципы и границы

- Backend state machine остаётся единственным источником состояния диалога.
- Qwen формулирует ответ, но не может самостоятельно менять статус, срочность, следующий обязательный шаг или решение об эскалации.
- Пользовательские ответы формируются только из найденных и разрешённых материалов базы знаний.
- При отсутствии подходящего материала, низкой уверенности, ошибке модели или нарушении схемы используется безопасный fallback либо оператор.
- На первом этапе не добавляются `pgvector`, отдельная embedding-модель, WebSocket, авторизация и сложная агентная логика.
- Сначала исправляются интеграционные дефекты и пять контрольных сценариев; визуальная полировка выполняется после них.

## 3. Целевая архитектура

```text
React Web
   │ REST + revision
   ▼
FastAPI Conversation API
   │
   ├── Dialogue state machine
   ├── Intent and safety rules
   ├── Knowledge retriever
   ├── Ollama answer generator
   ├── Output validator and fallback
   └── Escalation card builder
   │
   ├── PostgreSQL
   └── Approved Markdown/YAML knowledge base
```

### 3.1. Frontend

`apps/web` отображает состояние, полученное от backend, и не дублирует state machine. Создание обращения и отправка первого сообщения выполняются одной клиентской операцией: сначала создаётся разговор, затем сообщение отправляется с ID и revision из непосредственного ответа `POST /api/conversations`, а не из ещё не обновившегося React state.

Frontend обязан корректно обрабатывать:

- создание и восстановление обращения;
- отправку первого сообщения;
- `409 Conflict` и обновление актуального состояния;
- недоступность API;
- неизвестный или повреждённый формат ответа;
- состояния `RESOLVED` и `ESCALATED`;
- мобильную и настольную ширину.

### 3.2. Управление диалогом

Backend сначала применяет детерминированные правила:

1. приветствие, благодарность, просьба о помощи или операторе;
2. безопасность и немедленная эскалация;
3. извлечение уже известных фактов;
4. выбор подходящего playbook;
5. определение следующего вопроса или шага;
6. вызов RAG только там, где нужен ответ по базе знаний или естественная формулировка.

Статус изменяется только после успешной серверной валидации. Повторный вопрос не должен стирать ранее собранные факты.

### 3.3. RAG

Первый вариант использует локальный лексический поиск по Markdown/YAML без новой модели embeddings. Документы разбиваются на небольшие именованные фрагменты с идентификатором, сервисом, симптомами, разрешёнными шагами, рисками и условиями эскалации.

Пайплайн:

1. нормализовать запрос и известный контекст;
2. выбрать кандидатов по сервису и ключевым словам;
3. вычислить BM25-подобную оценку и взять несколько лучших фрагментов;
4. передать Qwen только историю, правила и выбранные фрагменты;
5. получить строгий JSON;
6. проверить схему, ссылки на источники, уверенность и безопасность;
7. показать ответ либо выполнить fallback/эскалацию.

Минимальный контракт ответа модели:

```json
{
  "answer": "Короткий ответ пользователю",
  "source_ids": ["vpn.connection.check-network"],
  "confidence": 0.84,
  "needs_operator": false,
  "reason": "Найден точный сценарий VPN"
}
```

`source_ids` должны быть подмножеством фактически переданных модели фрагментов. Ответ без источников допустим только для разговорных намерений, обрабатываемых правилами без RAG.

### 3.4. База знаний

Первая версия покрывает:

- VPN;
- CRM;
- корпоративную почту;
- пароль и вход;
- Wi-Fi и сеть;
- видеозвонки;
- права доступа;
- фишинг;
- массовую недоступность;
- неизвестную проблему.

Каждый документ содержит название, область применения, признаки, обязательные уточнения, безопасные шаги, запрещённые действия, условия эскалации и ответственную команду. Хакатонные документы и внутренний план проекта не входят в пользовательский поисковый корпус.

### 3.5. Валидация и fallback

Ответ Qwen отклоняется, если:

- JSON не соответствует схеме;
- указан неизвестный `source_id`;
- уверенность ниже порога;
- модель предлагает действие вне найденных материалов;
- ответ содержит опасное действие;
- запрос превысил timeout;
- Ollama недоступна.

При отклонении используется заранее проверенная формулировка playbook. Если playbook недостаточно, диалог переводится оператору с технической причиной fallback, не раскрываемой пользователю как внутренняя ошибка.

## 4. Incident Radar

Первая версия не требует отдельной ML-модели. Активные обращения нормализуются по сервису, симптомам и кодам ошибок. Кластер создаётся только при достижении минимального количества похожих обращений и порога сходства. Оператор видит предложение о массовом инциденте и подтверждает его; система не объявляет инцидент окончательно без подтверждения.

Минимальные операции:

- список предполагаемых инцидентов;
- связанные conversation ID;
- сервис, общие симптомы и количество обращений;
- подтверждение оператором;
- связь тикета с `incident_id`.

Рассылка обновлений и real-time транспорт остаются следующей итерацией.

## 5. Наблюдаемость

Для каждого диалога сохраняются:

- время первого полезного ответа;
- количество уточняющих вопросов;
- количество выполненных шагов;
- результат: решено или эскалировано;
- причина эскалации;
- использованный playbook и источники RAG;
- факт и причина fallback;
- длительность запроса Ollama.

Демонстрационные метрики рассчитываются только на контрольном наборе и не выдаются за статистику реального внедрения.

## 6. Тестирование

### 6.1. Обязательные уровни

- unit-тесты правил, retrieval, схем и fallback;
- backend API-тесты с PostgreSQL;
- frontend-тесты через MSW;
- интеграционный тест первого сообщения без моков;
- браузерная проверка с реальным backend;
- проверка запуска с выключенной Ollama.

### 6.2. Контрольные сценарии

1. CRM: срочная проблема решена.
2. VPN: несколько шагов и эскалация.
3. Фишинг: немедленная передача ИБ без опасных советов.
4. Неизвестная проблема: поиск ничего не нашёл, вызван оператор.
5. Массовый сбой: похожие обращения попадают в Incident Radar.

Каждый сценарий проверяет не только статус, но и отсутствие повторных вопросов, корректную историю шагов, источники ответа и полноту карточки оператора.

## 7. Приоритеты

### P0 — прямо сейчас

1. Создать интеграционную ветку от `develop` и объединить backend, AI и frontend.
2. Исправить потерю первого сообщения и добавить отсутствующий frontend-тест.
3. Добавить корректный `npm test` script.
4. Реализовать минимальный retrieval и валидируемый ответ Qwen.
5. Добавить утверждённые FAQ и связать их с существующими playbook.
6. Реализовать fail-closed fallback и причины эскалации.
7. Прогнать пять сквозных сценариев на PostgreSQL.
8. Зафиксировать единый запуск для macOS и Windows.

### P1 — после стабильного вертикального среза

1. Реализовать минимальный Incident Radar API и экран.
2. Улучшить операторскую карточку: ответы, шаги, источники и причина эскалации.
3. Добавить продуктовые метрики контрольного набора.
4. Подготовить seed-данные, четырёхминутный demo script и резервный режим без Ollama.
5. Выполнить надёжный тестовый деплой.

### P2 — после хакатонного MVP

- embedding-модель Ollama и гибридный поиск;
- `pgvector`;
- SSE/WebSocket;
- загрузка скриншотов;
- авторизация и роли;
- версионирование и экспертная оценка базы знаний;
- канальные интеграции;
- production-мониторинг и резервное копирование.

## 8. Распределение на четверых

| Роль | Текущая ответственность |
|---|---|
| Backend и диалог | RAG orchestration, валидация Qwen, fallback, API-контракты |
| Frontend | первое сообщение, обработка ошибок, UI-интеграция и браузерные сценарии |
| AI и знания | FAQ, playbook, retrieval-набор и оценка ответов |
| Оператор и интеграция | `develop`, Incident Radar, Docker, CI, деплой и демо |

Изменения общих контрактов проходят отдельной проверкой. Каждый участник работает в своей зоне, но интеграционная ветка обновляется после каждого завершённого вертикального изменения.

## 9. Критерии готовности ближайшей версии

- проект запускается по одной инструкции на macOS и Windows;
- первое сообщение не теряется;
- пять контрольных сценариев проходят через реальный интерфейс;
- Qwen отвечает только с разрешёнными источниками;
- ошибка или отсутствие Ollama не ломает диалог;
- неизвестный запрос передаётся оператору;
- оператор получает исходное обращение, факты, вопросы, шаги, результаты, источники и резюме;
- frontend build, lint и тесты, backend тесты и AI тесты проходят в CI;
- подготовлен воспроизводимый demo script и резервный сценарий.

## 10. Решения, отложенные намеренно

В ближайшую реализацию не входят сложная семантическая инфраструктура, автономный LLM-агент, мобильное приложение, полноценная production-аутентификация и real-time уведомления. Они не повышают надёжность обязательного четырёхминутного сценария настолько, чтобы оправдать риск и время до интеграции.
