# HelpFlow: аутентификация и разделение кабинетов

**Дата:** 2026-09-27  
**Статус:** согласованное направление, ожидает финального просмотра перед планом реализации

## Цель

Разделить пользовательский интерфейс сотрудника и специалиста, убрать переключение ролей из общей шапки и добавить полноценную аутентификацию для MVP. Сотрудник должен видеть только собственные обращения, специалист — только рабочую очередь. Регистрация, подтверждение адреса и восстановление пароля должны работать через реальные письма с личной Яндекс Почты владельца проекта.

## Границы MVP

В MVP входят:

- самостоятельная регистрация сотрудников;
- регистрация специалистов только по одноразовому приглашению;
- вход, выход и серверные сессии;
- подтверждение email;
- восстановление пароля;
- разграничение доступа по ролям;
- привязка обращений к сотруднику;
- отдельные интерфейсы сотрудника и специалиста;
- защита от перебора и злоупотребления почтовыми endpoint;
- SMTP через Яндекс с конфигурацией в окружении.

Не входят: социальный вход, SSO, MFA, полноценная администраторская панель, управление организациями и автоматическая обработка недоставленных писем.

## Роли и доступ

### Сотрудник (`employee`)

- самостоятельно создаёт аккаунт;
- обязан подтвердить email до работы с обращениями;
- попадает в `/employee`;
- создаёт обращения и видит только собственные диалоги;
- не имеет доступа к `/operator` и операторским API.

### Специалист (`operator`)

- создаёт аккаунт только по действующему приглашению;
- обязан подтвердить email;
- попадает в `/operator`;
- видит рабочую очередь и детали обращений;
- не использует интерфейс сотрудника как способ смены роли.

Роль хранится на сервере и не может выбираться или изменяться клиентом. При попытке открыть чужой кабинет интерфейс перенаправляет пользователя в его кабинет, а API возвращает `403`.

## Пользовательские маршруты

Публичные маршруты:

- `/login` — вход;
- `/register` — регистрация сотрудника;
- `/verify-email` — обработка ссылки подтверждения и повторная отправка;
- `/forgot-password` — запрос восстановления;
- `/reset-password` — установка нового пароля;
- `/operator/register?invite=...` — регистрация специалиста по приглашению.

Защищённые маршруты:

- `/employee` — кабинет сотрудника;
- `/employee/history` — история его обращений;
- `/operator` — очередь специалиста.

Корневой `/` перенаправляет гостя на `/login`, сотрудника на `/employee`, специалиста на `/operator`.

## Интерфейс

Публичные страницы используют отдельный auth-layout: логотип HelpFlow, короткое описание продукта и карточка формы. Внутри кабинета шапка показывает логотип, имя, роль, меню профиля и выход. Переключателей между ролями нет.

Формы отображают ошибки рядом с конкретным полем, общий ответ сервера — над кнопкой отправки. Во время запроса повторная отправка блокируется. После успешной регистрации пользователь попадает на экран ожидания подтверждения email. После подтверждения он может войти. После сброса пароля все его активные сессии отзываются.

## Валидация

Правила дублируются на клиенте для удобства, но окончательное решение всегда принимает сервер.

- имя и фамилия: обязательны, после обрезки пробелов 2–50 символов; допускаются Unicode-буквы, пробел, дефис и апостроф;
- email: обязательный, приводится к нижнему регистру, валидируется библиотекой, не длиннее 254 символов и уникален без учёта регистра;
- отдел: обязательное значение из `it`, `sales`, `marketing`, `finance`, `hr`, `operations`, `other`;
- пароль: 10–128 символов, минимум одна строчная и одна заглавная буква и цифра, без пробельных символов; проверяется совпадение подтверждения;
- согласие с правилами обязательно для регистрации сотрудника;
- токен приглашения обязателен для регистрации специалиста и используется один раз.

Сообщения о восстановлении пароля и повторной регистрации не раскрывают наличие адреса в системе. Для уже зарегистрированного неподтверждённого email сервер повторно отправляет подтверждение в пределах rate limit.

## Модель данных

### `users`

- `id` UUID;
- `first_name`, `last_name`;
- `email` с уникальным нормализованным индексом;
- `department`;
- `password_hash`;
- `role`: `employee` или `operator`;
- `email_verified_at`;
- `is_active`;
- `created_at`, `updated_at`, `last_login_at`.

### `auth_sessions`

- `id` UUID;
- `user_id`;
- `token_hash`;
- `expires_at`, `created_at`, `last_seen_at`, `revoked_at`;
- опциональные диагностические `user_agent` и усечённый IP-хеш без хранения исходного IP.

### `email_tokens`

- `id` UUID;
- `user_id`;
- `purpose`: `verify_email` или `reset_password`;
- `token_hash`;
- `expires_at`, `used_at`, `created_at`.

### `operator_invites`

- `id` UUID;
- `email` приглашённого специалиста;
- `token_hash`;
- `expires_at`, `used_at`, `created_at`.

В `conversations` добавляется nullable `owner_id` для совместимости с существующими демо-данными. Все новые обращения обязаны иметь владельца. Старые записи без владельца видны специалистам, но не сотрудникам.

## Безопасность сессий и паролей

Пароли хешируются Argon2id. Сырой пароль, SMTP-пароль и исходные одноразовые токены не сохраняются. Токены генерируются криптографически стойким генератором, в БД хранится SHA-256-хеш.

Случайный session token передаётся только в cookie со свойствами `HttpOnly`, `SameSite=Lax`, ограниченным `Path=/`; `Secure` включается вне локальной разработки. Сессия по умолчанию живёт 12 часов, при «Запомнить меня» — 30 дней. Выход отзывает текущую сессию, сброс пароля — все сессии пользователя.

Изменяющие состояние запросы дополнительно проверяют `Origin`/`Referer` против разрешённых origin. CORS остаётся с точным allowlist и credentials. В production API не допускает запуск с секретом или SMTP-паролем-заглушкой.

Rate limit применяется по endpoint и сочетанию IP/email: вход, регистрация, повторная отправка подтверждения и восстановление пароля. Счётчики могут быть процессными для локального MVP, но интерфейс rate limiter изолируется для будущего Redis.

## API

Основные endpoint:

- `POST /api/auth/register`;
- `POST /api/auth/operator/register`;
- `POST /api/auth/login`;
- `POST /api/auth/logout`;
- `GET /api/auth/me`;
- `POST /api/auth/verify-email`;
- `POST /api/auth/resend-verification`;
- `POST /api/auth/forgot-password`;
- `POST /api/auth/reset-password`.

Существующие conversation endpoint требуют подтверждённого сотрудника и принудительно используют его `user_id`; переданный клиентом владелец игнорируется. Operator endpoint требуют роль `operator`.

Ошибки используют единый формат с кодом, общим сообщением и необязательной картой ошибок полей. `401` означает отсутствие действующей сессии, `403` — недостаточную роль или неподтверждённый email, `422` — ошибки данных, `429` — превышение лимита.

## Почтовая доставка

Почтовый адаптер использует стандартный SMTP и настраивается переменными окружения:

- `SMTP_HOST=smtp.yandex.ru`;
- `SMTP_PORT=465`;
- `SMTP_SECURITY=ssl`;
- `SMTP_USERNAME`;
- `SMTP_PASSWORD` — отдельный пароль приложения;
- `SMTP_FROM_EMAIL`;
- `SMTP_FROM_NAME=HelpFlow`;
- `APP_PUBLIC_URL`.

Секреты находятся только в `.env`; `.env.example` содержит безопасные пустые значения и пояснения. Отправка выполняется после успешной фиксации пользователя/токена. При временной ошибке SMTP регистрация не откатывается: интерфейс сообщает, что аккаунт создан, но письмо не отправлено, и предлагает повторить отправку. Повторная отправка создаёт новый токен и инвалидирует предыдущие активные токены того же назначения.

Письма имеют текстовую и HTML-версию, не содержат паролей и объясняют срок действия ссылки. Ссылки строятся только из доверенного `APP_PUBLIC_URL`.

## Поток данных

1. Клиент валидирует форму и отправляет данные.
2. API повторно валидирует их, нормализует email и создаёт пользователя с хешем пароля.
3. API создаёт одноразовый email-токен и передаёт ссылку почтовому адаптеру.
4. Пользователь открывает ссылку; frontend отправляет токен в API.
5. API атомарно помечает токен использованным и подтверждает email.
6. При входе API проверяет пароль и подтверждение email, создаёт серверную сессию и выставляет cookie.
7. Frontend получает профиль через `/api/auth/me` и строит только подходящий роли кабинет.

## Миграция и совместимость

Добавляется Alembic-миграция с новыми таблицами и `conversations.owner_id`. Существующие conversation-тесты смогут явно подменять аутентификационную зависимость. Debug HTML-страницы остаются только локальными диагностическими инструментами и не считаются пользовательскими кабинетами; в production их следует отключать настройкой.

## Тестирование

Backend-тесты покрывают:

- регистрацию и все правила валидации;
- уникальность email без учёта регистра;
- Argon2-хеширование;
- одноразовость и срок жизни токенов;
- подтверждение email и восстановление пароля;
- отзыв сессий;
- запрет регистрации специалиста без приглашения;
- `401/403` для каждого защищённого endpoint;
- изоляцию обращений сотрудников;
- нейтральные ответы и rate limit;
- SMTP через тестовый адаптер без внешней сети;
- применение миграций к существующей БД.

Frontend-тесты покрывают формы, локальную валидацию, состояния загрузки, отображение серверных ошибок, role guards, перенаправления и отсутствие переключателя ролей. Сквозной smoke-сценарий проверяет регистрацию сотрудника, подтверждение, вход, создание обращения, выход и отдельный вход специалиста.

## Критерии готовности

- гость не видит ни один кабинет;
- сотрудник и специалист не могут открыть чужой интерфейс или API;
- новый сотрудник проходит регистрацию, получает настоящее письмо Яндекса, подтверждает email и входит;
- восстановление пароля работает по одноразовой ссылке и отзывает старые сессии;
- специалист регистрируется только по приглашению;
- сотрудник видит только свои обращения;
- секреты не попадают в репозиторий или ответы API;
- миграции, backend- и frontend-тесты проходят;
- интерфейс адаптивен и доступен с клавиатуры.
