# Управление пользователями, профили, метрики и безопасный RAG

Дата: 28 сентября 2026. Ветка: `codex/admin-rag-profiles`.

## Цель

Превратить текущий HelpFlow в управляемый корпоративный сервис:

- администратор сам создаёт и обслуживает аккаунты специалистов и редактирует аккаунты пользователей;
- специалисты видят личный профиль и основные показатели своей работы;
- администратор видит расширенные показатели каждого специалиста;
- администратор загружает правила и документы компании без ручного изменения YAML;
- Qwen отвечает не только по заранее заданным сценариям, но не выдаёт догадки за корпоративные факты;
- локальная Ollama отвечает заметно быстрее и предсказуемо передаёт сложные случаи человеку.

Текущие роли `employee`, `operator`, `admin`, сессионная авторизация, PostgreSQL и существующий операторский чат сохраняются.

## Принятые решения

### Создание специалиста вместо приглашения

`operator_invites` и регистрация специалиста по ссылке выводятся из основного пользовательского сценария. Администратор создаёт специалиста в разделе «Команда», передавая:

- одно поле `full_name`;
- рабочий email;
- подразделение.

Сервер создаёт пользователя с ролью `operator`, генерирует криптографически стойкий временный пароль и возвращает его только в ответе на создание. Сырой пароль не сохраняется и повторно не показывается. Администратор копирует данные и передаёт специалисту согласованным способом.

Новый флаг `must_change_password` принуждает специалиста заменить временный пароль сразу после первого входа. До замены пароля доступны только текущая сессия, выход и endpoint смены пароля. После замены отзываются остальные сессии пользователя.

### Административное управление аккаунтами

Администратор получает единый список всех пользователей с фильтрами по роли, статусу и поиском по имени/email. Разрешены:

- изменение ФИО, email и подразделения;
- смена роли `employee` / `operator` / `admin`;
- включение и отключение аккаунта;
- сброс пароля с выдачей нового временного пароля;
- просмотр времени создания и последнего входа.

Существующий пароль никогда не раскрывается: в базе остаётся только Argon2-хеш. Изменение email, роли, активности или пароля отзывает активные сессии. Email, установленный администратором, считается подтверждённым. Нельзя отключить или понизить последнего активного администратора. Самоотключение в текущей сессии запрещено.

Каждая административная операция записывается в `admin_audit_events`: actor, target, действие, время и безопасный JSON изменений без паролей и токенов.

## Профиль

Добавляется общая защищённая страница `/profile`, доступная из аватара в шапке.

Общая часть:

- ФИО, email, подразделение, роль;
- дата создания и последний вход;
- редактирование собственного ФИО и подразделения;
- смена пароля с проверкой текущего;
- выход.

Для специалиста дополнительно показывается компактная личная аналитика за 7 и 30 дней:

- сейчас в работе;
- ожидают его первого ответа;
- закрыто;
- медианное время первого ответа;
- медианное время решения;
- средняя оценка и количество оценок.

Сравнение с коллегами и рейтинг специалистов в личном профиле не показываются.

## Метрики администратора

Существующий `/api/admin/metrics` остаётся агрегированным дашбордом. Для детального просмотра добавляется endpoint метрик отдельного специалиста и экран/выдвижная карточка из таблицы команды.

Полный набор за выбранный период:

- текущая загрузка и число ожидающих первого ответа;
- назначено и закрыто;
- медиана и 90-й перцентиль первого ответа;
- медиана и 90-й перцентиль решения;
- средняя оценка и число оценок;
- доля ответов в целевое время;
- динамика закрытых обращений по дням;
- темы, срочность и доля повторных передач, если данные доступны.

Целевое время первого ответа задаётся конфигурацией, по умолчанию 15 минут. Вычисления делаются по данным `conversations`, без сохранения производных значений. Для специалиста используется тот же сервис, но response-схема исключает командные и сравнительные данные.

## База знаний администратора

Добавляется раздел `/admin/knowledge` и сущности:

- `knowledge_documents`: имя, исходное имя файла, MIME, размер, SHA-256, категория, версия, статус, активность, автор и timestamps;
- `knowledge_chunks`: document id, позиция, заголовок раздела, нормализованный текст и поисковые данные;
- `knowledge_processing_errors`: безопасное описание ошибки обработки.

Поддерживаемые форматы первой версии: PDF, DOCX, TXT и Markdown. Проверяются MIME, расширение, максимальный размер и число страниц. Файлы хранятся в выделенном Docker volume, метаданные и извлечённый текст — в PostgreSQL. Дубликат по SHA-256 не индексируется повторно.

Жизненный цикл документа:

`PROCESSING -> READY | FAILED -> ARCHIVED`.

Только активные документы `READY` участвуют в ответах. Администратор может открыть извлечённый текст, заменить версию, архивировать документ и повторить неудачную обработку. Физическое удаление в первой версии не используется, чтобы сохранять аудит источников старых ответов.

Обработка выполняется вне HTTP-запроса. Для MVP используется фоновая задача процесса с сохранённым статусом; интерфейс опрашивает статус. Контракт сервиса изолируется так, чтобы позже заменить выполнение очередью задач.

## Трёхуровневый контур ответов

### Уровень 1 — корпоративные документы

Гибридный поиск выбирает релевантные фрагменты активных документов и встроенной утверждённой базы. Для небольшого корпуса используется предрасчитанный нормализованный индекс в PostgreSQL и кэш готовых chunks в процессе API. Архитектура retrieval допускает добавление embeddings без изменения диалогового API.

Qwen получает вопрос, короткую историю и только выбранные фрагменты. Структурированный ответ содержит:

- короткий текст ответа;
- список утверждений;
- для каждого утверждения `source_id` и точную подтверждающую цитату;
- оценку достаточности источников;
- необходимость оператора.

Сервер принимает ответ только если каждый source id был передан модели, каждая цитата дословно присутствует в соответствующем chunk, отсутствуют запрещённые секреты и выполнены ограничения длины. Пользователь видит названия документов и раскрываемые цитаты.

### Уровень 2 — утверждённые сценарии HelpFlow

Существующие playbook применяются для типовых технических проблем, безопасности и пошаговой диагностики. Правила сохраняют контроль над срочностью, критическими инцидентами и эскалацией, но больше не требуют почти дословного совпадения ответа Qwen с заранее подготовленной фразой.

### Уровень 3 — общая рекомендация Qwen

Если корпоративного источника и подходящего playbook нет, Qwen может ответить из общих знаний только для низкорисковых технических вопросов. Такой ответ помечается «Общая рекомендация — не правило компании».

Разрешены только безопасные, обратимые действия без административных прав. Запрещено придумывать:

- внутренние адреса, контакты, учётные данные и сетевые настройки;
- корпоративные политики, сроки, права доступа и утверждённые процессы;
- HR-, финансовые, юридические и security-решения;
- команды, способные удалить данные или ослабить защиту.

Для запрещённых тем, низкой уверенности, повторной неудачи или просьбы пользователя создаётся передача специалисту с историей, найденными источниками и причиной отказа от автоматического ответа.

## Производительность

На один пользовательский ход допускается не более одного синхронного вызова Ollama. Правила, retrieval и safety gate выполняются локально до него.

- `keep_alive` удерживает Qwen в памяти;
- ответ ограничен примерно 300 токенами;
- в prompt попадают только лучшие короткие chunks и ограниченная история;
- частые нормализованные запросы и retrieval-результаты кэшируются;
- API прогревает модель после запуска, не блокируя health check;
- тайм-аут генерации по умолчанию 20 секунд;
- при тайм-ауте запрос не зависает: показывается честное сообщение и предлагается/выполняется передача специалисту;
- UI немедленно показывает состояние «Ищу в правилах компании»;
- небезопасный непроверенный текст модели никогда не стримится пользователю до валидации.

Целевые показатели локального MVP после прогрева: retrieval до 150 мс, детерминированный ответ до 500 мс, проверенный ответ Qwen — медиана до 8 секунд на доступном компьютере. Фактическая latency и причина fallback сохраняются для админской диагностики.

## API-контракты

Планируемые endpoints:

- `GET /api/admin/users`;
- `POST /api/admin/users/operators`;
- `PATCH /api/admin/users/{user_id}`;
- `POST /api/admin/users/{user_id}/reset-password`;
- `GET /api/admin/users/{user_id}/metrics?days=7|30`;
- `GET /api/profile`;
- `PATCH /api/profile`;
- `POST /api/profile/change-password`;
- `GET /api/profile/metrics?days=7|30`;
- `GET /api/admin/knowledge/documents`;
- `POST /api/admin/knowledge/documents`;
- `GET /api/admin/knowledge/documents/{document_id}`;
- `PATCH /api/admin/knowledge/documents/{document_id}`;
- `POST /api/admin/knowledge/documents/{document_id}/retry`.

Старые endpoints приглашений временно остаются совместимыми, но исчезают из UI и помечаются deprecated. После миграции и проверки их можно удалить отдельным изменением.

## Интерфейс

Раздел «Команда» становится каталогом пользователей: поиск, фильтры, компактная таблица, карточка редактирования и отдельное безопасное модальное окно временного пароля. Метрики специалиста открываются без перехода в операторскую очередь.

Профиль строится как полноценная рабочая страница: заголовок с ролью и статусом, личные показатели, блок данных аккаунта и отдельный блок безопасности. На мобильном все карточки складываются в одну колонку.

Раздел «База знаний» показывает загрузку drag-and-drop, прогресс обработки, статус, версию, размер, автора и действия. В чате рядом с корпоративным ответом отображается блок «Источники».

## Ошибки и безопасность

- загрузка, парсинг и модельные ошибки не раскрывают пути файлов и stack trace;
- архивный или неготовый документ не участвует в retrieval;
- prompt injection внутри документов и сообщений считается данными, а не инструкцией;
- изменение роли, email, статуса и пароля атомарно и аудируется;
- все write-endpoints сохраняют существующую проверку Origin/Referer;
- временный пароль не логируется, не сохраняется в аудите и не возвращается повторно;
- при конфликтующем редактировании клиент получает 409 и перезагружает свежую версию пользователя.

## Проверка

Обязательные тесты:

- создание специалиста, одноразовый временный пароль и принудительная смена;
- редактирование пользователя, отзыв сессий и защита последнего админа;
- разграничение полных и личных метрик;
- загрузка каждого формата, дубликаты, невалидные и слишком большие файлы;
- retrieval только по активным READY-документам;
- отклонение неизвестных source id и недословных evidence quotes;
- общий Qwen-ответ только для разрешённых низкорисковых тем;
- передача оператору для корпоративных вопросов без источника и при тайм-ауте;
- отсутствие второго LLM-вызова на одном ходе;
- frontend-тесты управления пользователями, профиля, метрик и базы знаний;
- PostgreSQL migration smoke и end-to-end demo flow.

## Порядок реализации

1. Миграции пользователей, временный пароль, аудит и admin API.
2. Админский каталог пользователей и новый сценарий создания специалиста.
3. Сервис метрик, детальные метрики администратора и личные метрики специалиста.
4. Профиль и безопасность аккаунта.
5. Документы, извлечение текста, статусы и админский интерфейс базы знаний.
6. Новый retrieval, три уровня ответа, evidence validation и тайм-ауты.
7. Интеграционная проверка, измерение latency, demo seed и документация.

Каждый этап должен быть отдельным небольшим коммитом с тестами и не менять публичный контракт следующего этапа без обновления этой спецификации.
