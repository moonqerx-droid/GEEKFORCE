# Incident Radar: отчёт

Ветка `codex/radar-and-polish` от `origin/main` (`0b4e277`). Сюда перенесены пять коммитов
`codex/incident-radar-p1` (cherry-pick, сама ветка не переписана) и доведена продуктовая часть.

![Радар у специалиста](screenshots/08-radar.png)

## Что сделано

### Перенос бэкенда радара
- Миграция радара теперь `20260927_0007` поверх `20260927_0006_operator_workflow`, в том же стиле:
  таблицы создаются, только если их ещё нет.
- Эндпоинты радара стоят рядом с `OperatorService` в `routes/operator.py` и закрыты
  `require_operator` (специалист и руководитель).
- Логика радара встроена поверх `triage.py` из `main` (`escalated_at`, сообщения в
  `ESCALATED`/`IN_PROGRESS`, `_escalate(..., message=...)`), фикстуры `conftest.py` объединены.

### Продуктовая часть
- **Специалист.** Над очередью блок «Массовые проблемы»: сервис, сколько сотрудников затронуто,
  когда пришло первое обращение, статус («Похоже на сбой» или «Подтверждён»). По клику в центре
  открывается сбой:
  - чьи обращения в него попали и что каждый написал своими словами;
  - почему их объединили (совпавшие признаки);
  - кнопка «Подтвердить сбой»;
  - одно сообщение всем затронутым;
  - «Сбой устранён» закрывает сбой и все его обращения.

  В очереди обращения из сбоя помечены «Общий сбой», по участнику сбоя можно открыть его обращение.
- **Сотрудник.** Если первое сообщение совпало с известным сбоем, помощник сразу отвечает
  «Похоже, это общий сбой: VPN не работает у нескольких коллег, специалисты уже чинят» и добавляет
  последнее обновление, если оно было. Диагностики нет. Под чатом панель «Сбой уже чинят».
  Сообщения специалиста приходят в чат обычным опросом раз в 3 секунды, с именем специалиста.
- **Руководитель.** На дашборде блок «Массовые сбои сейчас» со ссылкой на сбой в рабочем месте.
- **Демо-данные.** `seed_demo` добавляет свежий сбой VPN (ошибка 809) у пяти сотрудников за
  последние 30 минут. Все обращения проходят через настоящий движок: первые три после диагностики
  уходят специалисту и образуют сбой, остальные присоединяются на первом сообщении. Повторный запуск
  добавляет сбой, только если открытого сбоя VPN нет.

### Найденные и исправленные ошибки
- С `autoflush=False` (так работает `SessionLocal` в приложении) у нового сбоя была пустая
  сигнатура, и к нему никто не мог присоединиться. В тестах это не проявлялось: там сессия
  с автосбросом.
- Служебные слова («пишет», «опять», «помогите») считались признаками сбоя и уводили похожие
  обращения ниже порога.
- Дашборд руководителя прокручивался вбок на ширине 390 px. Проблема была и до радара, поправил.

## Как проверить руками

1. `docker compose up -d --build`, затем `docker compose exec api python -m app.seed_demo`,
   потом фронт `cd apps/web && npm run dev`. Пароль всех аккаунтов `DemoPass123`.
2. `anna@helpflow.demo` (специалист), раздел «Обращения»: над очередью «VPN не работает у 5
   сотрудников». Откройте его. Видно пятерых сотрудников и их слова, признаки «809, vpn,
   подключается».
3. «Подтвердить сбой», затем напишите «Сервер VPN перезапускаем, ориентир 15 минут» и нажмите
   «Отправить 5 сотрудникам».
4. `ivan@helpflow.demo`, «Мои обращения»: в обращении про VPN есть сообщение Анны. Новое
   обращение «VPN не подключается, пишет ошибка 809» сразу получает ответ про общий сбой с последним
   обновлением. Вопросов и шагов нет.
5. `admin@helpflow.demo`, «Обзор»: блок «Массовые сбои сейчас».
6. Снова Анна: «Сбой устранён», затем «Закрыть N обращений». У сотрудников обращения становятся
   «Решено» с итоговым сообщением, сбой пропадает из списка.

## Изменения API

Все добавочные, существующие поля и эндпоинты не менялись.

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/operator/incidents?include_resolved=` | открытые сбои |
| POST | `/api/operator/incidents/{id}/broadcast` | сообщение всем: `{message, request_key, expected_revision}` |
| POST | `/api/operator/incidents/{id}/confirm` | подтвердить: `{expected_revision}` |
| POST | `/api/operator/incidents/{id}/resolve` | закрыть сбой и обращения: `{message, expected_revision}` |

Новые необязательные поля `IncidentRead`: `service_label`, `affected_employees`, `first_seen_at`,
`members[] {id, status, owner_name, owner_department, original_request, created_at}`.
Новая настройка `INCIDENT_WINDOW_MINUTES` (по умолчанию 120): только обращения, переданные
специалисту за это время, могут образовать новый сбой. Миграция `20260927_0007_incident_radar`.

## Принятые решения

1. **Окно в 2 часа** для образования сбоя. Иначе старые обращения из истории склеивались бы в
   «сбой» с новыми. Присоединение к уже открытому сбою окном не ограничено.
2. **В сбой попадают и обращения, которые специалист уже взял** (`IN_PROGRESS`), не только ждущие.
3. **Рассылка — сообщение специалиста** (`role=operator`, с автором), а не помощника. Она
   фиксирует `first_operator_reply_at`: сотрудник получил ответ человека. На метрики это влияет
   честно. Обращения при этом ни на кого не назначаются.
4. **«Сбой устранён» закрывает все его открытые обращения** (`resolved_by=operator`). Сотрудник
   видит итог и может оценить решение. В исходной спецификации автоматическое закрытие было
   отложено, но без него у сценария нет конца.
5. **Заголовок считает людей, а не обращения**: «у 5 сотрудников», даже если у кого-то два
   обращения. Список обращений показывает все.
6. **Логотип и README** перенесены в отдельную ветку `claude/jury-readme`: она строится от более
   свежей сборки `claude/test-stand`. Скриншот радара лежит здесь, `docs/screenshots/08-radar.png`.

## Что не сделано

- Сигнатура сбоя лексическая. Перефразировки без общих слов («впн не коннектится» без кода ошибки)
  могут не присоединиться. Для отбора это осознанно: поведение объяснимо и воспроизводимо.
- Нет автоматического закрытия сбоя по времени и нет истории прошлых сбоев в интерфейсе, хотя
  API отдаёт закрытые через `include_resolved=true`.
- Старый отладочный `/debug/operator` радар не показывает, он есть только в основном интерфейсе.
