# GEEKFORCE HelpFlow — единый план команды

> Главный рабочий документ команды. Все архитектурные решения, задачи и изменения объёма работ сверяются с этим файлом.

## 1. Цель проекта

Создать виртуального помощника технической поддержки, который проводит пользователя через полный цикл решения проблемы:

1. принимает свободное, неполное или эмоциональное описание;
2. понимает суть проблемы, сервис, симптомы и обстоятельства;
3. определяет срочность и объясняет её причину;
4. задаёт только те вопросы, которые нужны для текущей проблемы;
5. предлагает действия по одному шагу;
6. после каждого шага узнаёт результат и выбирает продолжение;
7. подтверждает, что проблема действительно решена;
8. при необходимости передаёт специалисту готовое обращение со всем собранным контекстом.

Ключевой вопрос продукта:

> Что произошло, насколько это срочно и что нужно сделать, чтобы решить проблему?

Важно: мы создаём не универсальную службу поддержки и не обычный чат с LLM. Мы демонстрируем несколько качественно проработанных сценариев от первого сообщения до решения или эскалации.

## 2. Рабочее название и позиционирование

**Название:** GEEKFORCE HelpFlow.

**Короткое описание:** AI-помощник, который превращает эмоциональное обращение сотрудника в управляемый процесс решения проблемы.

**Главный тезис защиты:**

> Мы автоматизировали не ответ на вопрос, а весь путь обращения: от эмоционального описания до подтверждённого решения или передачи специалисту с полностью подготовленным контекстом.

## 3. Основной пользовательский сценарий

Демонстрационное сообщение:

> Не могу войти в CRM с ноутбука, но с телефона работает. Через 20 минут встреча.

Ожидаемое поведение системы:

1. Определить сервис `CRM`.
2. Выделить симптомы: не работает на ноутбуке, работает на телефоне.
3. Поставить высокий приоритет из-за встречи через 20 минут.
4. Кратко объяснить пользователю, что система поняла.
5. Спросить только недостающую информацию, например текст ошибки или наличие VPN.
6. Предложить первый диагностический шаг.
7. Получить результат шага.
8. При ответе «не помогло» предложить альтернативный сценарий.
9. При ответе «помогло» подтвердить восстановление доступа и закрыть обращение.
10. При невозможности решения передать специалисту заполненную карточку.

## 4. Обязательные функции MVP

### 4.1. Обращение пользователя

- ввод проблемы в свободной форме;
- поддержка неполных, неточных и эмоциональных формулировок;
- отсутствие требования знать технические термины или категорию обращения.

### 4.2. Понимание проблемы

Система извлекает:

- краткую суть;
- затронутый сервис;
- симптомы;
- уже известные обстоятельства;
- срочность и её причину;
- недостающую информацию;
- предполагаемый сценарий решения;
- уверенность классификации.

### 4.3. Уточняющие вопросы

- каждый вопрос должен влиять на следующий шаг;
- нельзя спрашивать то, что уже есть в истории;
- максимум 1–3 вопроса перед началом решения;
- при срочном обращении путь должен быть короче.

### 4.4. Пошаговое решение

- пользователю показывается один шаг за раз;
- после шага доступны ответы «Помогло», «Не помогло», «Не могу выполнить»;
- отрицательный результат меняет следующий шаг;
- инструкции должны быть короткими и безопасными.

### 4.5. Проверка результата

- система явно спрашивает, восстановилась ли нужная функция;
- обращение закрывается только после подтверждения пользователя;
- если решение не помогло, система продолжает другой сценарий либо выполняет эскалацию.

### 4.6. Передача специалисту

Карточка эскалации включает:

- исходное обращение;
- уточняющие вопросы и ответы;
- предполагаемую проблему;
- уровень и причину срочности;
- выполненные действия;
- результат каждого действия;
- текущий статус;
- краткое AI-резюме;
- другую важную информацию.

Пользователь не должен заново описывать ситуацию специалисту.

## 5. Контр-фича: Incident Radar

**Incident Radar** объединяет похожие обращения в возможный массовый инцидент.

Пример похожих сообщений:

- «Не открывается корпоративный портал»;
- «Ошибка 502 в CRM»;
- «Не могу зайти в рабочую систему».

Система должна:

- сравнивать новое обращение с активными обращениями;
- создавать кластер при достаточном сходстве;
- показывать оператору возможный массовый инцидент;
- связывать подходящие обращения;
- сообщать пользователю, что проблема может быть массовой;
- не заставлять каждого пользователя проходить одну и ту же диагностику;
- позволять оператору отправить обновление всем связанным пользователям.

Эта функция создаёт отдельный пользовательский сценарий, полезна пользователю и специалисту и должна быть встроена в основной продукт, а не показана отдельным прототипом.

Рекомендуемый стек:

- React/Next.js для интерфейсов;
- FastAPI для backend;
- SQLite на время хакатона;

- Docker Compose;

Логическое разделение компонентов нужно для параллельной разработки. Не следует тратить время на сложную production-микросервисную инфраструктуру.

## 7. Общая модель обращения

Состояния:

```text
NEW
→ ANALYZING
→ CLARIFYING
→ TROUBLESHOOTING
→ VERIFYING
→ RESOLVED | ESCALATED
```

Минимальная модель данных:

```text
Conversation
├── id
├── status
├── created_at
├── updated_at
├── summary
├── service
├── symptoms[]
├── urgency
├── urgency_reason
├── known_facts{}
├── missing_facts[]
├── confidence
├── playbook_id
├── messages[]
├── completed_steps[]
├── escalation_summary
└── incident_id
```

Ожидаемый структурированный ответ AI:

```json
{
  "summary": "Пользователь не может войти в CRM с ноутбука",
  "service": "CRM",
  "symptoms": ["не открывается на ноутбуке", "работает на телефоне"],
  "urgency": "high",
  "urgency_reason": "встреча через 20 минут",
  "known_facts": {},
  "missing_facts": ["текст ошибки", "тип подключения"],
  "next_question": "Какое сообщение появляется при входе?",
  "confidence": 0.86,
  "recommended_playbook": "crm_login_device_specific",
  "should_escalate": false
}
```

## 8. API-контракт

Эти маршруты фиксируются в начале разработки:

```text
POST /api/conversations
POST /api/conversations/{id}/messages
POST /api/conversations/{id}/step-result
POST /api/conversations/{id}/escalate
GET  /api/conversations/{id}
GET  /api/operator/tickets
GET  /api/operator/incidents
POST /api/operator/incidents/{id}/broadcast
```

После согласования контрактов `packages/contracts` меняет только ответственный за backend через отдельный PR. Остальные участники используют утверждённые типы или моки.

## 9. Распределение работы на четырёх участников

### Участник 1 — пользовательский Frontend

**Зона владения:** `apps/web`.

**Ветка:** `feat/user-interface`.

Задачи:

- экран начала обращения;
- чат пользователя и помощника;
- состояния «анализирую» и «проверяю решение»;
- карточка распознанной проблемы;
- отображение срочности и её причины;
- пошаговые инструкции;
- кнопки результата шага;
- экран успешного решения;
- экран передачи специалисту;
- статус массового инцидента;
- адаптивная мобильная версия;
- работа с моками до готовности API.

**Definition of Done:** пользователь может пройти основной сценарий целиком через интерфейс, включая отрицательный результат шага и эскалацию.

### Участник 2 — Backend и управление диалогом

**Зоны владения:** `apps/api`, `packages/contracts`.

**Ветка:** `feat/backend-workflow`.

Задачи:

- API и общие схемы;
- хранение обращений и сообщений;
- конечный автомат диалога;
- создание и изменение тикета;
- фиксация выполненных действий;
- генерация карточки передачи;
- API операторской панели;
- SSE или WebSocket для обновления статуса;
- SQLite и миграции;
- seed-данные для демонстрации.

**Definition of Done:** состояние диалога хранится на backend, запрос можно восстановить после обновления страницы, а эскалация содержит полную историю.

### Участник 3 — AI/LLM и база знаний

**Зоны владения:** `services/ai`, `knowledge-base`.

**Ветка:** `feat/ai-triage`.

Задачи:

- классификация обращения;
- извлечение структурированных данных;
- оценка срочности;
- определение недостающей информации;
- выбор одного следующего вопроса;
- поиск инструкции в базе знаний;
- выбор следующего шага после неудачи;
- решение об эскалации;
- краткое резюме для оператора;
- тестовые сценарии;
- стабильный fallback без внешнего LLM API.

База знаний содержит 8–12 качественных playbook-сценариев:

- вход и пароль;
- VPN;
- CRM;
- корпоративная почта;
- сеть/Wi-Fi;
- видеозвонки;
- права доступа;
- недоступность сервиса;
- подозрение на массовый сбой;
- неизвестная проблема.

**Definition of Done:** AI возвращает валидный JSON по общей схеме, не повторяет уже заданные вопросы и проходит контрольные сценарии.

### Участник 4 — операторская панель, Incident Radar и интеграция

**Зоны владения:** `apps/operator`, `services/incidents`, `.github`, документация и деплой.

**Ветка:** `feat/operator-incidents`.

Дополнительная роль: лидер интеграции и продукта.

Задачи:

- очередь обращений;
- сортировка по срочности;
- полная карточка эскалации;
- кластеризация похожих обращений;
- экран массового инцидента;
- рассылка статуса связанным пользователям;
- Docker Compose;
- CI;
- деплой;
- README и инструкция запуска;
- сценарий презентации;
- резервная локальная демоверсия.

**Definition of Done:** специалист видит приоритетную очередь, получает полный контекст и может создать либо обновить массовый инцидент.

## 10. Правила работы с GitHub

Структура веток:

```text
main
└── develop
    ├── feat/user-interface
    ├── feat/backend-workflow
    ├── feat/ai-triage
    └── feat/operator-incidents
```

Правила команды:

- никто не пушит напрямую в `main`;
- один PR решает одну законченную задачу;
- PR создаётся сразу в режиме Draft;
- каждый PR проверяет хотя бы один участник;
- участники не изменяют чужие каталоги без согласования;
- общие типы изменяются отдельным PR;
- ветки обновляются из `develop` минимум два раза в день;
- в `main` вливается только проверенная `develop`;
- за 3–4 часа до защиты вводится feature freeze;
- после feature freeze разрешены только исправления и улучшения демонстрации.

Формат коммитов:

```text
feat(chat): add troubleshooting step card
feat(ai): extract urgency from free-form request
fix(api): preserve completed troubleshooting steps
test(flow): cover urgent unresolved request
docs(plan): update team responsibilities
```

GitHub Issues:

```text
EPIC-1 User experience
EPIC-2 Conversation workflow
EPIC-3 AI triage
EPIC-4 Operator cockpit and Incident Radar
```

Каждая задача должна иметь ответственного, критерии готовности, зависимости и одну из меток: `must-have`, `demo`, `nice-to-have`.

## 11. План выполнения

### Этап 1 — общий старт, 60–90 минут

Вся команда вместе:

- утверждает основной пользовательский путь;
- фиксирует API и схемы данных;
- создаёт структуру проекта;
- выбирает окончательный стек;
- создаёт issues и ветки;
- определяет визуальное направление;
- фиксирует данные демонстрации.

После этого участники переходят в свои зоны и работают параллельно.

### Этап 2 — первый вертикальный срез

Как можно раньше должен заработать один путь от первого сообщения до закрытия обращения.

Порядок:

1. Ввести срочное сообщение о CRM.
2. Получить структурированный анализ.
3. Ответить на уточняющий вопрос.
4. Получить первый шаг.
5. Нажать «Не помогло».
6. Получить альтернативный шаг.
7. Нажать «Помогло».
8. Закрыть обращение.

Пока этот сценарий не проходит целиком, команда не начинает необязательные функции.

### Этап 3 — обязательные сценарии кейса

| Сценарий | Ожидаемое поведение |
|---|---|
| Простая проблема | Решение без лишних вопросов |
| Неоднозначное описание | 1–3 уточнения, затем решение |
| Несколько симптомов | Выделение симптомов и поиск общей причины |
| Нерешаемая проблема | Эскалация с полным контекстом |
| Срочное обращение | Высокий приоритет и сокращённый путь |
| Массовый инцидент | Объединение похожих запросов и общее обновление |

### Этап 4 — интеграция Incident Radar

Создать три seed-обращения с общей причиной. Четвёртое обращение во время демонстрации должно:

- попасть в существующий кластер;
- изменить интерфейс пользователя;
- появиться в операторской панели;
- получить общее обновление статуса.

### Этап 5 — стабилизация

- запретить новые крупные функции;
- проверить пустые, длинные и странные сообщения;
- добавить понятные ошибки API;
- убрать заметные задержки;
- проверить fallback без LLM;
- подготовить локальный запуск;
- записать резервное видео;
- провести минимум три репетиции с таймером.

## 12. Критерии готовности продукта

Продукт готов к защите только если:

- пользователь может описать проблему свободным текстом;
- система извлекает несколько фактов из одного сообщения;
- срочность имеет понятное объяснение;
- каждый вопрос влияет на дальнейший путь;
- инструкции выдаются по одному шагу;
- отрицательный результат меняет сценарий;
- есть явная проверка результата;
- эскалация сохраняет всю историю;
- оператору не нужно перечитывать чат целиком;
- Incident Radar работает в основном продукте;
- все шесть сценариев воспроизводимы;
- проект запускается одной командой;
- существует резервный режим без внешнего AI API.

## 13. Что нельзя тратить время делать

- универсальную базу знаний на сотни тем;
- сложную авторизацию и управление организациями;
- полноценный production-мониторинг;
- собственную ML-модель с обучением;
- мобильное приложение вместо адаптивного web-интерфейса;
- красивую функцию, которая не участвует в демонстрации;
- длинные ответы LLM без управляемой логики процесса.

При выборе между шириной и качеством всегда выбираем один полностью работающий сценарий.

## 14. Сценарий защиты на 4 минуты

### 0:00–0:25 — проблема

«Сотрудники не знают технических терминов, пишут эмоционально, а поддержка затем заново собирает контекст».

### 0:25–1:40 — основной сценарий

Показать:

- сложное срочное обращение;
- извлечённые симптомы;
- срочность и её причину;
- один релевантный вопрос;
- последовательные шаги;
- проверку результата.

### 1:40–2:30 — эскалация

Показать нерешённую проблему и открыть операторскую панель. Специалист уже должен видеть, что произошло, что уточняли, что пробовали и что не помогло.

### 2:30–3:20 — Incident Radar

Показать обнаружение похожих обращений, создание общего инцидента и уведомление связанных пользователей.

### 3:20–4:00 — эффект

Показать метрики, которые система умеет измерять на тестовых сценариях:

- количество вопросов до решения;
- доля самостоятельно решённых обращений;
- время подготовки обращения для специалиста.

Нельзя выдавать демонстрационные значения за результаты реального внедрения.

## 15. Приоритеты при нехватке времени

Порядок, в котором нельзя нарушать приоритеты:

1. Полный основной сценарий.
2. Корректная эскалация.
3. Пять обязательных тестовых случаев.
4. Рабочий Incident Radar.
5. Надёжный деплой и fallback.
6. Визуальная полировка.
7. Любые дополнительные функции.

## 16. Риски и защита от них

| Риск | Что делаем |
|---|---|
| LLM отвечает нестабильно | Строгая JSON-схема, валидация, повтор запроса и mock fallback |
| Участники блокируют друг друга | Сначала фиксируем контракты, затем работаем по отдельным каталогам |
| Конфликты при merge | Маленькие PR, владельцы каталогов, регулярное обновление из `develop` |
| Падает интернет или API | Локальный режим и заранее сохранённые ответы для демо |
| Не хватает времени | Срезаем функции строго снизу списка приоритетов |
| Демо выглядит как обычный чат | Показываем состояние процесса, проверку результата, операторскую панель и Incident Radar |

## 17. Ежедневный контроль команды

Короткий синк два раза в день, максимум 10 минут. Каждый отвечает:

1. Что уже работает в продукте?
2. Что будет готово к следующей интеграции?
3. Что блокирует работу?
4. Какой PR требуется проверить?

После каждого синка ответственный за интеграцию обновляет issues и собирает `develop`.

---

**Правило команды:** если функция не помогает обязательному сценарию или четырёхминутной демонстрации, она не является приоритетной.
