# HelpFlow

<img src="apps/web/public/brand/helpflow-mark.svg" width="56" align="right" alt="HelpFlow">

Помощник техподдержки для сотрудников компании. **Сотрудник не пересказывает проблему дважды: специалист получает готовую карточку.**

Сотрудник пишет как есть, даже на эмоциях: «опять всё сломалось, через 20 минут встреча». Помощник понимает, что сломалось и насколько срочно, задаёт только те вопросы, от ответа на которые зависит следующий шаг, и ведёт к решению по одному шагу. Если не помогло, обращение уходит специалисту вместе с исходными словами, ответами, выполненными шагами и причиной передачи, а специалист отвечает в том же чате. Это не «чат с LLM»: диалогом управляют правила и утверждённые сценарии, поэтому модель не может выдумать шаг или корпоративное правило. О правилах компании помощник отвечает только по документам, которые загрузил руководитель, и показывает цитату; чужие пароли и ключи не сообщает никогда.

Кейс хакатона «Поддержка, которая не бесит» (Актион × Уфимский университет), команда GEEKFORCE.

## Как закрыты требования кейса

| Требование кейса | Как сделано |
|---|---|
| 1. Принять обращение свободным текстом | Поле «Что случилось?»: своими словами, можно с эмоциями. К сообщению прикладываются фото, скриншоты и файлы (PDF, TXT, LOG, DOCX, XLSX) до 10 МБ, до пяти за раз, скриншот вставляется прямо из буфера через ⌘V / Ctrl+V. Опечатки и разговорные слова понимаются: «ранботало», «принтр не пичатает», «комп жутко тупит». Приветствие, «спасибо», «позовите человека» распознаются отдельно и не запускают диагностику. |
| 2. Понять суть, сервис, обстоятельства и чего не хватает | Движок выбирает сценарий, сервис, срочность с причиной («встреча через 20 минут») и достаёт из текста уже названные факты: устройство, VPN, текст ошибки, ресурс. Справа «Карточка обращения» показывает, что понял помощник. |
| 3. Задать только нужные вопросы | Вопрос задаётся, только если ответ меняет следующий шаг и его ещё нет в тексте. Не больше трёх, при срочности — один. На закрытые вопросы отвечают одной кнопкой («В браузере», «Да», «Не знаю»), поле для своих слов остаётся. Повторов нет, это проверяют тесты. |
| 4. Предложить шаги по одному и узнать результат | Карточка шага с тремя исходами: «Помогло», «Не помогло», «Не получается выполнить». Можно ответить и словами: «получилось», «не нашёл, где это» — помощник поймёт. Если посреди разговора названа ещё одна проблема («а ещё интернет пропал»), она записывается в обращение; первопричина вроде интернета разбирается первой. |
| 5. Проверить, решена ли проблема; если нет — сменить сценарий | После «Помогло» помощник спрашивает, всё ли работает. «Нет, всё ещё не работает» ведёт к следующему, другому шагу, а когда шаги кончились — к специалисту. |
| 6. Передать специалисту готовую карточку | Исходное обращение, вопросы и ответы, предполагаемая проблема, выполненные шаги с результатами, текущий результат, причина передачи и команда. Специалист отвечает в том же чате, сотрудник видит его ответ. |

Пять типов тестовых обращений, как они ведут себя на стенде:

| Тип | Пример | Что делает помощник |
|---|---|---|
| Простое | «Забыл пароль от учётки, не срочно» | Срочность низкая, вопросов нет, сразу шаг «Сбросьте пароль через портал самообслуживания». |
| Неоднозначное | «Ничего не работает, помогите пожалуйста» | Один вопрос «На что это похоже?» с кнопками: вход или пароль, почта, VPN, интернет, медленная работа, доступ, другое. Нажатие «Почта» (или ответ словами «не открывается outlook») переключает на сценарий почты. |
| Несколько симптомов | «Outlook не синхронизируется, а ещё в Zoom нет звука и интернет постоянно отваливается» | Находит все три проблемы, говорит об этом и начинает с интернета как корневой причины. Остальные разбирает следом. Если дело дойдёт до специалиста, все три проблемы со статусами попадут в карточку эскалации (поле `issues` в API). |
| Нерешаемое самостоятельно | «Нужен доступ к папке бухгалтерии на общем диске» | Не переспрашивает названный ресурс: объясняет, что доступ выдают администраторы, и сразу передаёт заявку команде «Администраторы доступа». |
| Срочное | «Через 5 минут звонок с клиентом, не запускается Teams, горит!» | Срочность «высокая» с причиной. Первым идёт самый быстрый обходной путь (подключиться с телефона или через браузер), вопросов про гарнитуру нет. |

Как помощник отвечает, от надёжного к осторожному:

| Уровень | Когда | Пример на стенде |
|---|---|---|
| Сценарий | вопрос подходит под один из 13 утверждённых сценариев | «Забыл пароль от почты» → шаг «Сбросьте пароль через портал самообслуживания» |
| Документ компании | ответ есть в документе из «Базы знаний» | «Какие суточные положены в командировке?» → «По документу «Регламент командировок»: Суточные… 700 рублей в день…», с цитатой источника |
| Общая рекомендация | безопасное обратимое действие, документа нет | «Как очистить кэш браузера?» → «Общая рекомендация — не правило компании…» |
| Передача специалисту | правила компании без документа, доступы, безопасность, сомнения | «Сколько дней отпуска мне положено?» → сразу специалисту |

### Как мы проверяем качество ответов

Не «на глаз»: 153 эталонных диалога в `apps/api/tests/golden/dialogues.yaml` написаны так, как пишут живые сотрудники, — с опечатками, «не знаю», ответами не на тот вопрос и новой проблемой посреди разговора. Измеритель проигрывает их через настоящий сервис диалога и считает, угадан ли сценарий, сколько вопросов до первого полезного действия, нет ли мусора в карточке и повторных вопросов:

```bash
cd apps/api && PYTHONPATH=../../services/ai python -m app.eval_dialogues --semantic
```

| Что проверяем | Результат |
|---|---|
| Поведение в диалоге (37 многоходовых диалогов) | 100 % |
| Понимание формулировки (116 фраз) | 97 % |
| Свежие фразы, написанные до настройки (честная контрольная группа, 40) | 90 % (78 % без смыслового слоя) |
| Проверки из условия кейса, `scripts/check-case.py` | 10 из 10 |

Порог качества стоит в CI (`tests/test_golden_dialogues.py`): изменение, которое ухудшает ответы, не пройдёт. Как устроено понимание и почему выбраны эти модели — `docs/ai-models.md`. Сценарий демо-видео с проверенными фразами — `docs/demo-script.md`.

Чужие и служебные учётные данные помощник не выдаёт: на «Скажи пароль администратора от сервера» он отвечает, что пароли, ключи и токены не сообщает, и передаёт запрос администраторам доступа. «Ввёл пароль на подозрительном сайте» — инцидент ИБ: инструкция отключиться от сети и сразу специалист.

Пример из кейса («опять всё сломалось… через телефон открывается, с ноутбука нет… через 20 минут встреча») распознаётся как вход в рабочую систему с одного устройства. Срочность высокая по причине «встреча через 20 минут», задаётся один вопрос: что появляется на ноутбуке. Подозрение на фишинг и массовые сбои уходят специалисту сразу, с инструкцией отключиться от сети в случае ИБ.

## Контр-фича: Incident Radar

Когда ломается общий сервис, в поддержку приходят десятки одинаковых обращений: каждого сотрудника гоняют по одной и той же диагностике, а специалисты отвечают каждому отдельно. Радар замечает, что за последние два часа пришло три похожих обращения про один сервис, и объединяет их в сбой.

- **Специалист** видит над очередью «Массовые проблемы»: сервис, скольких людей задело и с какого времени. Внутри — кто пострадал, что каждый написал и по каким признакам обращения объединены. Он подтверждает сбой, отправляет одно сообщение всем пострадавшим, а по «Сбой устранён» закрывает сбой вместе со всеми обращениями.
- **Сотрудник** видит подтверждённый сбой ещё до того, как начал писать: над «Что случилось?» плашка «VPN: известный сбой, уже чиним» и кнопка «У меня то же самое». Неподтверждённые догадки радара сотрудникам не показываются.
- **Сотрудник**, чьё обращение похоже на известный сбой, сразу получает ответ: «Похоже, это общий сбой: VPN не работает у нескольких коллег, специалисты уже чинят». Лишних шагов нет, обновления приходят в его чат.
- **Руководитель** видит активные сбои на дашборде.

Похожесть считается детерминированно, без LLM и внешних сервисов: взвешенное совпадение значимых слов, кода ошибки и сервиса, порог 0,55. Поэтому результат объясним и одинаков на любом компьютере.

## Роли и экраны

**Сотрудник** видит свои обращения списком слева, как в мессенджере: в работе и решённые. Он описывает проблему, прикладывает скриншот, отвечает на вопросы, проходит шаги и видит справа, что понял помощник. Если нужен человек, специалист подключается в тот же чат. ## Архитектура

```mermaid
flowchart LR
    U[Браузер<br/>React: сотрудник, специалист, руководитель] -->|HTTP, сессия в cookie| API[FastAPI]
    API --> DB[(PostgreSQL<br/>обращения, пользователи, сбои, аудит)]
    API --> E[Движок правил<br/>services/ai]
    E --> KB[Утверждённые сценарии<br/>13 YAML и статьи]
    API -->|готовые фрагменты| E
    DB --- DOC[Документы компании<br/>PDF, DOCX, TXT, MD<br/>загружает руководитель]
    API --> R[Incident Radar<br/>детерминированное сходство]
    E -. один ограниченный вызов,<br/>только формулировка .-> Q[Qwen в Ollama<br/>опционально]
    Q -. JSON с цитатами источников .-> V{Проверка:<br/>источник передан,<br/>цитата дословная}
    V -->|подтверждено| E
    V -->|нет| H[Ответ сценария<br/>или специалист]
```

Правила решают, какой вопрос задать, какой шаг показать и когда передать специалисту. Qwen получает только уже выбранные фрагменты и может сформулировать ответ по ним, но не может поменять шаг, вопрос или решение об эскалации. Корпоративные вопросы без документа (отпуск, доступы, безопасность, финансы) не отвечаются: они уходят специалисту. Ответ по документу показывает сотруднику цитату; при вызове Qwen каждое утверждение модели проверяется на дословное совпадение с переданным фрагментом, иначе ответ не показывается.

## Техническая часть

- API: FastAPI, SQLAlchemy, Alembic, PostgreSQL в Docker, SQLite для быстрых тестов.
- AI-движок `services/ai/helpflow_ai`: правила, 13 YAML-сценариев в `knowledge-base/`, проверка цитат, опциональная Ollama/Qwen или OpenAI-совместимый провайдер.
- Фронтенд: React 19, Vite, TypeScript, vitest и msw.
- Тесты: pytest для API (включая PostgreSQL smoke в CI) и для AI, vitest для фронтенда, GitHub Actions.

Проверить весь базовый сценарий на запущенном стенде: `./scripts/smoke-p0.sh` (в Windows `./scripts/smoke-p0.ps1`). Swagger: <http://localhost:8000/docs>.

Остановить: `docker compose down`. Данные PostgreSQL лежат в volume `helpflow-postgres-data`; при старте Compose применяет миграции Alembic и только потом запускает API.

### Настройка писем через Яндекс Почту

Регистрация и восстановление пароля используют настоящий SMTP. Для локального MVP:

1. включите двухфакторную аутентификацию в Яндекс ID;
2. создайте отдельный пароль приложения для почты;
3. скопируйте `.env.example` в `.env`;
4. заполните `SMTP_USERNAME`, `SMTP_PASSWORD` и `SMTP_FROM_EMAIL`;
5. оставьте `SMTP_HOST=smtp.yandex.ru`, `SMTP_PORT=465`, `SMTP_SECURITY=ssl`;
6. задайте `APP_PUBLIC_URL` адресом frontend-приложения, например `http://localhost:5174`.

Обычный пароль от Яндекс ID использовать нельзя. Файл `.env` исключён из Git; не вставляйте почтовый пароль в исходный код, Dockerfile или команду запуска. Для production укажите HTTPS-адрес приложения и `COOKIE_SECURE=true`.

После регистрации HelpFlow отправляет письмо подтверждения. Ссылки подтверждения и сброса пароля одноразовые и ограничены по времени. Если SMTP временно недоступен, аккаунт сохраняется, а письмо можно запросить повторно.

Для командной разработки достаточно одинаковой команды на macOS и Windows. При необходимости скопируйте `.env.example` в `.env` и замените `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` и `DATABASE_URL` согласованно. Значения по умолчанию предназначены только для локальной разработки.

## Миграции базы данных

В Docker миграции применяются автоматически перед запуском API. При локальной разработке из `apps/api`:

```bash
alembic upgrade head
```

Откатить последнюю миграцию:

```bash
alembic downgrade -1
```

Локальный запуск без Docker по умолчанию использует `sqlite:///./helpflow.db`. Чтобы подключиться к PostgreSQL вручную, задайте `DATABASE_URL=postgresql+psycopg://user:password@host:5432/database` перед запуском Alembic и API.

## AI и совместимость

Новые обращения используют `services/ai/helpflow_ai`: вопросы, шаги и карточки берутся из `knowledge-base`. Без внешнего ключа рекомендуется локальная Ollama: задайте `AI_PROVIDER=ollama`, `OLLAMA_MODEL=qwen3.5:9b` и `OLLAMA_BASE_URL=http://host.docker.internal:11434` в корневом `.env`. Docker Desktop передаст запросы в Ollama на macOS или Windows. Для запуска API напрямую без Docker используйте `OLLAMA_BASE_URL=http://localhost:11434`.

Проверьте Ollama командой `ollama list`, затем из корня пересоздайте API через `docker compose up -d --build`.

**Понимание свободного текста** устроено слоями, и каждый работает локально и бесплатно:

1. Исправление опечаток и словоформы (`pymorphy3` + `rapidfuzz`): «принтр не пичатает», «в очереди печати» — всегда включено, ~1 мс.
2. Смысловое сравнение с живыми примерами из сценариев (поле `examples:` в YAML) через эмбеддинги `bge-m3` в Ollama: «комп жутко тупит», «скинь пароль от админки». Включается само при `AI_PROVIDER=ollama`, нужна модель: `ollama pull bge-m3` (~1,2 ГБ). ~100 мс на сообщение; без Ollama движок молча остаётся на правилах. Отключить: `SEMANTIC_MATCHING=off`.
3. Правила безопасности (ИБ, запрос чужих паролей, массовый сбой) смысловой слой не переопределяет.

Качество меряется эталонными диалогами: `cd apps/api && python -m app.eval_dialogues` (добавьте `--semantic`, чтобы включить смысловой слой). Замеры — в `docs/ai-models.md`. Классификация и управление диалогом остаются быстрыми детерминированными правилами. Для подходящего технического запроса Qwen получает только найденные утверждённые фрагменты базы знаний и возвращает строгий JSON; неизвестный источник, низкая уверенность или ошибка модели дают безопасный ответ правил. Для полностью автономного режима без Ollama задайте `AI_PROVIDER=rules`. `AI_PROVIDER=mock` также отключает сетевые запросы и предназначен прежде всего для тестов. OpenAI-совместимый внешний сервис можно включить через `AI_PROVIDER=openai`, `AI_API_KEY`, `AI_BASE_URL` и `AI_MODEL`.

Рекомендуемая конфигурация `.env` для локальной Qwen:

```dotenv
AI_PROVIDER=ollama
OLLAMA_BASE_URL=http://host.docker.internal:11434
OLLAMA_MODEL=qwen3.5:9b
AI_TIMEOUT_SECONDS=20
```

Вызов Ollama ограничен: один запрос на сообщение, подключение 2 с, ответ до 20 с, `num_predict=320`, `num_ctx=4096`, `keep_alive=15m` (`OLLAMA_*` в `.env`). Если модель не ответила вовремя, диалог продолжается по правилам или передаётся специалисту, бесконечного ожидания нет.

LLM может улучшать понимание, содержательный ответ по базе знаний и резюме, но не может менять выбранный шаг, вопрос или решение об эскалации. Ответ модели показывается, только если каждое утверждение подтверждено дословной цитатой из переданного фрагмента; иначе остаётся ответ сценария или обращение уходит специалисту. Файл `.env` исключён из Git.

Существующие обращения сохраняют прежнюю логику через `workflow_version=legacy`. Новые получают `triage-v1`. HTTP-контракт сохраняет значения `normal` и `cannot_perform`; адаптер переводит их в AI-значения `medium` и `cannot_do`. В ответ добавлена `escalation_card` с причиной передачи, командой, вопросами, шагами и текущим результатом.

В standalone-запуске AI читает настройки из переменных окружения процесса; `.env` автоматически подставляет Docker Compose. Подробности модуля — в [services/ai/README.md](services/ai/README.md). Проверка AI: `pytest services/ai/tests` из корня после `pip install -e services/ai`.

Debug UI (`/debug`, `/debug/operator`) предназначен для локальной отладки. Основной интерфейс — React-приложение с входом по ролям.

Результаты изучения веток команды и точки интеграции — в [docs/integration-status.md](docs/integration-status.md).
